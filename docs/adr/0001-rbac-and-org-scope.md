# ADR-0001. Модель ролей, прав и принадлежности к оргструктуре

- **Статус:** принято (этап A)
- **Дата:** 22.10.2026
- **Связано с:** ТЗ v1.0, разделы 3, 3.1, 13, 17 (п. 5)

## Контекст

Портал закрытый, для одной группы компаний. Доступ должен ограничиваться одновременно
*действием* (что можно делать) и *областью* (над какой частью оргструктуры). Требования:
запрет по умолчанию, проверка на сервере на каждом запросе, несколько ролей у пользователя,
администратор компании не может выйти за пределы своей компании и не может выдать себе
или другим больше прав, чем имеет сам. Роли не должны «зашиваться» строками в бизнес-логику.

## Решение

### 1. Оргструктура

`company_groups → companies → dealerships → departments`.

- Таблица названа `company_groups`, а не `groups`: `GROUPS` — зарезервированное слово MySQL 8.
- `departments.dealership_id` допускает `NULL` — отдел уровня компании (например, общий колл-центр).
- Каждая сущность хранит **денормализованный путь**: `group_id`, `company_id`, `dealership_id`
  (насколько применимо). Родитель после создания **неизменяем** — перенос подразделения
  в другую компанию не поддерживается, чтобы денормализованный путь и история не расходились.
  Если перенос понадобится, это отдельная операция с пересчётом и аудитом.
- Удаления нет: подразделения деактивируются (`is_active = false`).

### 2. Идентичности

- `User` — учётная запись (логин/пароль). `Employee` — сотрудник, может не иметь учётной записи.
- Связь 1:1 опциональна: `users.employee_id` (UNIQUE, NULL). Вместо отдельной таблицы
  `user_employee_links` из ориентира ТЗ — связь хранится в колонке, история изменений — в аудите.
- `CallParticipant` (говорящий) появится на этапе C и с этими сущностями не смешивается.
- У пользователя есть **домашнее подразделение** (`group_id`, `company_id`, `dealership_id`,
  `department_id`, заполняется до нужного уровня). Оно определяет, кто может управлять
  этой учётной записью. Это не то же самое, что области ролей.
- У сотрудника есть основная компания (`employees.company_id`) и назначения
  `employee_assignments` (компания / центр / отдел, должность, даты начала и окончания).

### 3. Права

- Права — фиксированный реестр кодов (`App\Domain\Identity\Permission`, enum). Код
  проверяет **только права**, никогда не коды ролей. Реестр синхронизируется в таблицу
  `permissions` командой `php artisan avtoklass:sync-permissions` (выполняется сидером).
- К перечню ТЗ добавлены: `organization.view`, `employees.view`, `employees.manage`
  (просмотр оргструктуры и справочника сотрудников отделён от управления ими).
- Роль — именованный набор прав, хранится в БД и редактируется из интерфейса.
  Начальные шаблоны ролей создаются сидером; в коде их коды не используются.
- `roles.allowed_scope_types` ограничивает, на каком уровне роль можно назначать
  (например, роль «Суперадминистратор» — только на уровень группы).

### 4. Области (scopes)

Назначение роли: `user_role_scopes(user_id, role_id, scope_type, scope_id)`,
`scope_type ∈ {group, company, dealership, department, own}`. Для `own` `scope_id = 0`.

Область **наследуется вниз**: назначение на компанию покрывает её центры, отделы, сотрудников
и пользователей. `own` — только записи, связанные с собственным сотрудником пользователя.

Итоговое право = объединение по всем назначениям пользователя, где роль содержит право.
`AccessScope` для пары (пользователь, право) — множества `group_ids`, `company_ids`,
`dealership_ids`, `department_ids` и флаг `own`. Используется двумя способами:

1. **Фильтр запросов** — `Model::scopeVisibleTo($user, $permission)` добавляет
   `WHERE group_id IN (…) OR company_id IN (…) OR …` по денормализованному пути.
   Пустая область → `WHERE 1 = 0` (запрет по умолчанию).
2. **Проверка конкретного объекта** — Policy сравнивает путь объекта с областью.

Объекты чужой области в API отдаются как **404**, а не 403, чтобы не раскрывать их существование.

### 5. Защита от эскалации

- Выдать роль R в области S можно, только если у выдающего есть **каждое** право роли R
  в области, покрывающей S, плюс `users.update` над целевым пользователем.
  Отзыв назначения подчиняется тому же правилу.
- Изменять/отключать пользователя, менять ему пароль и завершать его сессии можно, только
  если домашнее подразделение пользователя **и все** его назначения ролей лежат в области
  действующего. Так администратор компании A не может отключить пользователя, имеющего
  роль в компании B или в группе.
- Следствие: администратор компании может назначать роли директора, РОП, контролёра и
  сотрудника, только если сам обладает их правами в своей компании. Поэтому шаблон
  «Администратор компании» включает бизнес-права этих ролей (звонки, оценки, аналитика) —
  в пределах своей компании. Если заказчик захочет «администратора без доступа к звонкам»,
  понадобится отдельное право делегирования; это осознанно отложено.
- Создание и изменение ролей (`roles.manage`) требует права на уровне **группы** —
  глобальные роли меняет только суперадминистратор (ТЗ, разд. 17, п. 5).
- Нельзя отнять у системы последнего активного пользователя с `roles.manage`
  на уровне группы (защита от потери управления).
- Изменение набора прав роли использует оптимистическую блокировку (`lock_version`).

### 6. Аудит

`audit_events` хранит автора, действие, объект, путь в оргструктуре (для фильтрации
по области `audit.view`), IP, user-agent, `changes` (старое/новое значения) и причину.
Чувствительные поля (`password`, `remember_token`, токены) **никогда** не пишутся —
только факт изменения. Изменения моделей фиксируются автоматически через трейт
`Auditable`; события безопасности (вход, выход, неудачный вход, сброс пароля,
завершение сессий, выдача/отзыв ролей) — явно.

### 7. Аутентификация SPA

SPA обслуживается тем же Laravel-приложением на том же домене. API `/api/v1` работает на
middleware-группе `web`: серверная сессия в БД, cookie `HttpOnly`, CSRF через
`XSRF-TOKEN`/`X-XSRF-TOKEN` (стандартный механизм Laravel и axios). Отдельный пакет
токенов (Sanctum) не нужен, пока нет внешних API-клиентов. Сессии в БД позволяют
показать пользователю его сессии и завершить их.

## Последствия

- Любая новая сущность, которая должна фильтроваться по области, обязана хранить
  денормализованный путь (`group_id` … `department_id`) и подключить трейт `HasOrgScope`.
- Исторические снимки оргструктуры в карточке звонка (этап B) — отдельная задача:
  путь звонка фиксируется на момент приёма и не пересчитывается при переводе сотрудника.
- MFA для администраторов в этапе A не реализована; это обязательное условие
  промышленного запуска (см. «Известные ограничения» в README).
