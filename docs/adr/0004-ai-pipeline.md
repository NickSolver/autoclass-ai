# ADR-0004. Конвейер ИИ: распознавание, оценка, провайдеры (этап C)

- **Статус:** принято
- **Дата:** 24.10.2026
- **Связано с:** ТЗ v1.0, разд. 5, 7, 8, 12, 15 (этап C); ADR-0003

## Решения

1. **Провайдеры — сменяемые драйверы.** Интерфейсы `SpeechToTextProviderInterface` и
   `EvaluationProviderInterface`; конфигурации — в админке (`provider_configs`): основной и резервный
   на каждый вид, тайм-аут, тарифы, ключ API. Ключ хранится зашифрованным (`APP_KEY`), задаётся отдельной
   операцией, никогда не возвращается и не пишется в журнал; изменение ключа и ролей — с повторным кодом MFA.
2. **Драйверы этапа C:**
   - `mock` — тестовый провайдер внутри портала (распознавание и оценка). Распознавание **не распознаёт
     речь**: синтетический диалог по длительности записи, помечен `is_synthetic`, в интерфейсе — «ТЕСТОВЫЕ
     ДАННЫЕ». Оценка — сопоставление фраз демо-критериев; неизвестные критерии — `insufficient_data`.
     Режимы сбоев (тайм-аут, 429, 500, плохой JSON, выдуманная цитата, неверные таймкоды) — для проверки
     конвейера без внешних сервисов.
   - `openai_compatible` — оценка через OpenAI-совместимый Chat Completions API: `POST {endpoint}/chat/completions`,
     `Authorization: Bearer`, `response_format: json_object`, ответ `choices[0].message.content`, расход
     `usage.prompt_tokens/completion_tokens`, ошибки `{"error": {"message", ...}}`. Готовая настройка — DeepSeek
     (`https://api.deepseek.com`, `deepseek-chat`). Схема сверена с живым API DeepSeek 24.10.2026 (сайт
     документации из сети заказчика недоступен; ответы 401 и формат ошибки проверены запросами без ключа).
     Распознавания речи у DeepSeek нет — нужен отдельный провайдер (будет отдельным драйвером после выбора).
   - Других провайдеров нет: их API не придумываются (ТЗ, разд. 4.3, 8).
3. **Запрет внешней обработки по умолчанию** (ТЗ, разд. 12). Внешний драйвер нельзя сделать основным или
   резервным, пока суперадминистратор не разрешит передачу — с причиной, повторным кодом MFA и аудитом.
   Запрет снимает внешних провайдеров с ролей сразу. Адрес внешнего API — только `https`, не внутренние
   адреса (защита ключа и от SSRF); сообщения провайдера очищаются от фрагментов ключа.
4. **Конвейер** (ТЗ, разд. 5): подготовка → распознавание → классификация → оценка → «Готово».
   Если провайдер следующего шага не включён — статусы `awaiting_transcription` / `awaiting_evaluation`.
   Каждый шаг — отдельная идемпотентная задача с историей попыток. Временные сбои (тайм-аут, 429, 5xx) —
   повтор (до `analysis.tries`, на 429 — через время из `Retry-After`), на последней попытке — резервный
   провайдер; ошибки конфигурации (401, 402, нет ключа) — без повторов. Окончательная ошибка — статус
   «Ошибка обработки» с причиной; запись и звонок не теряются.
5. **Расшифровка проверяется до сохранения:** отрезки в пределах записи (±0,5 с), по порядку, непустые.
   Версии расшифровки неизменяемы. Роль говорящего — гипотеза, не установление личности.
6. **Ответ модели** — строгий JSON (`PromptBuilder::schema()`); расшифровка передаётся как недоверенные
   данные между маркерами, с запретом выполнять инструкции из речи. Сервер проверяет: JSON-объект, та же
   версия чек-листа, каждый критерий ровно один раз, допустимый статус (иначе — один контролируемый
   повтор запроса, затем ошибка шага); доказательства: реплика существует, цитата дословно в реплике
   (без учёта регистра, ё/е, кавычек), говорящий совпадает, отрезок времени возможен. Таймкоды
   доказательства берутся из реплики, а не из ответа модели. Отклонённое доказательство сохраняется с
   причиной, критерий и результат уходят на проверку человеку.
7. **Оценка (правило v1, ТЗ разд. 7.1):** pass = вес, fail = 0, N/A вне знаменателя; `insufficient_data` и
   критерии с отклонёнными доказательствами не подменяются — «Требуется вмешательство человека», итоговое
   число не публикуется (хранится предварительное по разрешённым критериям); знаменатель 0 — `null`;
   критическое нарушение — флаг, обнуление — только если включено в версии чек-листа. Основной и
   дополнительные чек-листы — раздельные результаты.
8. **Чек-листы:** модель данных версий и критериев — сейчас; конструктор — этап D. Созданы три DEMO-чек-листа
   (ТЗ, разд. 7.3) с пометкой «не для кадровых выводов». Выбор чек-листов до конструктора процессов —
   **временное** правило `config/analysis.php` по направлению звонка.
9. **Журнал вызовов** (`ai_provider_calls`): провайдер, модель, операция, версия шаблона запроса, хеш
   входа, время, секунды аудио / токены, стоимость по тарифу конфигурации, ошибка, попытка. Содержимое
   записей, расшифровок и ответов не пишется. Просмотр — отдельное право `ai.logs.view`.

## Не входит в этап C

Ручная проверка и исправления (этап E: очередь, решения, апелляции); правка расшифровки человеком;
конструкторы (этап D); настоящий провайдер распознавания речи (после выбора); выбор провайдера
для оценки по качеству на эталонной выборке (этап F/пилот).
