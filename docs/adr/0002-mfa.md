# ADR-0002. Двухфакторная аутентификация (MFA)

- **Статус:** принято
- **Дата:** 23.10.2026
- **Связано с:** ТЗ v1.0, разд. 3.1 («MFA для администраторов как обязательная опция до промышленного запуска»); ADR-0001

Решения согласованы с заказчиком (все варианты «по умолчанию»).

## Решения

1. **Способ — TOTP** (RFC 6238): 6-значный код в приложении-аутентификаторе (Яндекс Ключ,
   Google/Microsoft Authenticator и т. п.). Без SMS-провайдера, без передачи номеров третьим лицам.
   QR-код генерируется на сервере (bacon/bacon-qr-code), внешние сервисы не используются.
2. **Кому обязательна** — обладателям хотя бы одного права управления (`Permission::requiringMfa()`):
   `users.create/update/disable`, `roles.manage`, `organization.manage`, `employees.manage`,
   `integrations.manage`, `ai.manage`, `audit.view`. Определяется по правам, а не по ролям.
   Остальные могут подключить MFA добровольно (и отключить).
3. **Когда спрашивать** — при каждом входе; можно отметить устройство доверенным на 30 дней
   (случайный токен в зашифрованной HttpOnly-cookie, в БД — только SHA-256).
4. **Восстановление** — 10 одноразовых резервных кодов (в БД — SHA-256), показываются один раз;
   сброс администратором, который управляет пользователем (`users.update` над ним и всеми его ролями,
   ADR-0001), с обязательной причиной; себе сбросить нельзя. Аварийный сброс с сервера:
   `php artisan avtoklass:mfa-reset <login>`. После сброса льготный период не возобновляется —
   подключить MFA нужно при следующем входе.
5. **Ввод в действие** — 7 дней льготного периода с первого входа после появления обязательности;
   в это время в интерфейсе висит напоминание. Затем без MFA доступны только экраны подключения и выхода.
6. **Повторное подтверждение** — назначение/отзыв ролей, создание/изменение/удаление ролей, сброс чужой MFA,
   временный пароль другому пользователю, новые резервные коды и отключение своей MFA требуют кода,
   введённого не раньше 15 минут назад. Доверенное устройство это время не обновляет.
   Пока у пользователя MFA не подключена (льготный период), повторное подтверждение не требуется.

## Реализация

- Секрет TOTP хранится в `users.mfa_secret` с шифрованием `APP_KEY` (cast `encrypted`).
  **Смена `APP_KEY` сделает секреты нечитаемыми** — всем потребуется сброс MFA.
- Повтор уже использованного кода отклоняется (`users.mfa_last_timestep`).
- Неверные коды: не больше 5 в минуту на пользователя; каждая ошибка — в аудит.
- Порядок проверок в API: вход → второй фактор (`mfa`) → смена временного пароля → права.
  Ответы 403 содержат `code`: `mfa_verification_required`, `mfa_setup_required`, `mfa_confirmation_required`.
- Интерфейс на `mfa_confirmation_required` открывает диалог кода и повторяет исходный запрос автоматически.
- Ограничители частоты запросов — именованные (у каждого свой счётчик): безымянные `throttle:N,M`
  делят один счётчик на пользователя, из-за чего общий лимит API блокировал ввод кода.

## Требования к эксплуатации

- Время на сервере синхронизировано (NTP), иначе коды не совпадут. Допуск — ±30 секунд.
- У администраторов есть смартфоны с приложением-аутентификатором, разрешённым политикой компании.
