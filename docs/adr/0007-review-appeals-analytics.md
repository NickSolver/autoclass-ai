# ADR-0007. Ручная проверка, апелляции и аналитика (этап E)

- **Статус:** принято
- **Дата:** 26.10.2026
- **Связано с:** ТЗ v1.0, разд. 5, 10, 11, 16 (этап E); ADR-0004, ADR-0006

## Решения

1. **Ревизии вместо перезаписи.** Правка оценки человеком создаёт новую строку `evaluation_results`
   (`origin = human`, `revision + 1`, `supersedes_id`, автор, причина). Прежняя ревизия, включая результат ИИ,
   не меняется: у неё снимается только признак `is_current`. Подтверждение без правок новой ревизии не создаёт:
   оно отмечает `approval_state = human_confirmed` и пишет решение. Критерии исправленной ревизии хранят
   `previous_status`. Оценка пересчитывается тем же правилом v1. Каждое решение — неизменяемая строка
   `review_decisions` (кто, когда, причина, изменения критериев), а также событие аудита со старым и новым значением.
2. **Итоговый результат** — последняя ревизия (`is_current`) в действующем анализе звонка
   (`calls.current_analysis_run_id`, последний успешный). Повторная обработка начинает новый анализ: открытые
   проверки по прежнему закрываются, по новому при необходимости создаются заново.
3. **Проверки** (`manual_reviews`) создаются автоматически: при «Требуется вмешательство человека» или по задаче
   бизнес-процесса. Вручную — по праву `review.assign`. Жизненный цикл: ожидает → в работе (взял исполнитель
   с `review.resolve`) → решена / отменена. Решение нужно по каждому чек-листу звонка: подтверждение требует
   `evaluation.finalize`, исправление — `evaluation.override`. Параллельные изменения отсекает `lock_version`.
   Исключение звонка закрывает его проверки. Перенос звонка в другое подразделение переносит область его
   проверок и апелляций.
4. **Апелляции** подаёт пользователь с правом `appeal.create` (сотрудник — по своим звонкам, область own).
   Решает независимый пользователь с `appeal.resolve`: не автор, не сотрудник звонка и не тот, кто выставил или
   подтвердил оспариваемую ревизию. Независимость проверяет сервер, список кандидатов на назначение уже отфильтрован.
   Принятая апелляция исправляет оценку (новая ревизия), отклонённая оставляет оценку и записывает решение
   с обоснованием. Автор может отозвать апелляцию.
5. **Исправление расшифровки** (`transcript.edit`) — новая версия с источником `human` и причиной. Оценка
   автоматически не пересчитывается: только явной повторной обработкой (ТЗ, разд. 17, п. 3).
6. **Аналитика** (`analytics.view`, область права). Используются честные знаменатели:
   - средняя оценка — по основному чек-листу и только по итоговым результатам с числовой оценкой;
   - результаты без оценки показаны отдельно и в среднюю не входят;
   - дополнительные чек-листы — отдельной таблицей;
   - доля критических нарушений — от звонков с итоговой оценкой;
   - исключённые звонки не оцениваются;
   - всегда показываются период, объём выборки, разбивка по версиям чек-листов и итоговость
     (ИИ / подтверждено / исправлено человеком).

   Стоимость считается без подмены нулём: вызовы без тарифа показаны отдельно. Конверсия — «нет данных»:
   договорённость в текущем промпте не извлекается, CRM нет.
7. **Выгрузка** (`analytics.export`) — CSV для Excel (UTF-8 с BOM, разделитель «;»), с защитой от формул.
   Каждая выгрузка пишется в аудит вместе с фильтрами.

## Последствия

- Старые результаты ИИ не удаляются и всегда доступны в истории оценки.
- Звонки, оценённые до этапа E, получили действующий анализ миграцией данных.
- Уведомлений о новых задачах нет (модуля уведомлений нет). Очередь доступна на экране «Ручные проверки».
