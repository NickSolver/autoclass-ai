# ADR-0008. Подключаемые источники звонков (этап F, каркас)

- **Статус:** принято
- **Дата:** 27.10.2026
- **Связано с:** ТЗ v1.0, разд. 4.1–4.4, 12, 15 (этап F); ADR-0003

## Решения

1. **Единый договор адаптера** — `CallSourceDriver` (ТЗ, разд. 4.1):
   - `getCapabilities` (pull / push / записи), `configFields`, `validateConfiguration`, `testConnection`;
   - `fetchBatch(cursor)`, `resolveRecording`, `normalize`, `verifyWebhook`, `webhookPayloads`.

   Адаптер не пишет в БД: он нормализует данные (`NormalizedCall`), а импорт выполняет ядро.
2. **Calltouch и «Лягушка» перечислены в реестре, но кода интеграции нет.** Их API не придумывается
   (ТЗ, разд. 4.3–4.4): в интерфейсе — «ждёт документации», подключение создать нельзя. Работает
   **тестовый источник** с собственным, явно тестовым форматом и подписью. Он даёт синтетические звонки,
   записи-тоны и режимы сбоев (неверный ключ, недоступность, запись не по схеме, звонки без записи).
   Этап F не считается завершённым без реальных адаптеров (ТЗ, разд. 15).
3. **Подключение** (`source_connections`) задаёт:
   - область: компания и, при необходимости, центр или отдел, в которые попадают звонки;
   - настройки по полям адаптера и интервал синхронизации;
   - ключ доступа — зашифрован, только запись, с повторным кодом MFA;
   - адрес приёма событий — случайный токен и отдельный секрет подписи. Секрет показывается один раз,
     смена требует MFA.

   Подключение создаётся выключенным. Управление — по праву `integrations.manage` в области подключения.
4. **Идемпотентность.** `calls.external_id = "{подключение}:{внешний ID}"` при уникальности `source_id + external_id`:
   повтор выгрузки, повтор события и параллельные сеансы не создают дублей. Курсор сохраняется после каждой
   порции, поэтому повтор после сбоя продолжает с места остановки.
5. **Сопоставление.** Сотрудник определяется по добавочному в компании подключения — только при
   однозначном совпадении, иначе он «не установлен» (ТЗ, разд. 17, п. 4). Звонки не склеиваются по номеру
   телефона. Подразделение берётся из настроек подключения, иначе из действующего назначения сотрудника.
6. **Записи** проходят ту же проверку, что и ручная загрузка (`AudioIntake`: сигнатура, ffprobe,
   длительность, хеш, приватное хранилище); совпадение хеша отмечается как вероятный дубль. Звонок без
   записи учитывается в статусе «ожидает запись» и не оценивается (ТЗ, разд. 10).
7. **Журнал.**
   - Каждое событие хранится в `source_events`: внешний ID, канал, результат (принят / дубль / без записи /
     ошибка), ссылка на звонок. Сырой payload зашифрован и наружу не отдаётся.
   - Номер клиента у звонка хранится только маскированным.
   - Сеансы синхронизации (`source_sync_runs`) хранят курсоры, счётчики и ошибку.
8. **Исполнение.**
   - Pull: сервис `scheduler` (`schedule:work`) каждую минуту ставит в очередь подключения, у которых подошёл
     интервал. Задача уникальна на подключение, сеанс защищён блокировкой.
   - Push: `POST /api/v1/source-webhooks/{token}` — без сессии и CSRF, с ограничением частоты и проверкой
     подписи адаптером. События сохраняются и импортируются в очереди. Неизвестный или выключенный адрес
     даёт 404.

## Что нужно для реальных адаптеров

Документация API и тестовый доступ: авторизация, выгрузка звонков с курсором или окном времени, получение
записей, формат и подпись вебхуков, схема идентификаторов и добавочных, ограничения частоты, тестовая среда.
После этого адаптер реализует `CallSourceDriver`, а ядро, хранение и интерфейс не меняются.
