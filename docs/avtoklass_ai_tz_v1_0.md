# Автокласс AI — техническое задание v1.0

**Статус:** согласованная концепция + предлагаемые технические решения; документ для проектирования и поэтапной реализации ИИ-агентом.  
**Дата:** 22.10.2026.  
**Исходная основа:** «Универсальная платформа автоматического анализа и контроля качества телефонных звонков для сети автомобильных дилерских центров ГК Автокласс» (10 страниц) и ответы заказчика в переписке.  
**Стек:** Laravel / Vue 3 / TypeScript / MySQL; инфраструктурные компоненты Redis, FFmpeg и приватное объектное хранилище.

> **Статусы решений:** **[УТВЕРЖДЕНО]** — прямо указано заказчиком; **[РЕКОМЕНДОВАНО]** — предложено на основе практик, можно принять как рабочий default до пересмотра; **[ТРЕБУЕТ ПРОВЕРКИ]** — нельзя считать установленным фактом (например, интерфейс провайдера и юридическая допустимость передачи записи).

## 1. Назначение и границы

**[УТВЕРЖДЕНО]** Создать закрытый внутренний портал для *одной группы компаний*, включающей несколько (ориентировочно до десятка, точное число не фиксируется) компаний, дилерских центров, отделов и сотрудников. Анализировать телефонные звонки, формировать проверяемые оценки и рекомендации, предоставлять отчёты по областям ответственности. **Это не SaaS**: отсутствуют самостоятельная регистрация внешних клиентов, мультиарендная подписка, биллинг.

**[УТВЕРЖДЕНО]** Источники подключаются модульно: ручная загрузка входит в ядро и доступна по умолчанию; Calltouch и телефония «Лягушка» подключаются отдельно как независимые интеграционные модули. Отсутствие модуля не мешает работе ядра.

**[УТВЕРЖДЕНО]** Администратор конфигурирует сценарии и оценки из веб-интерфейса по принципу бизнес-процессов CRM: **визуальный конструктор с ветвлениями**. Один звонок может получать **основную и дополнительные** оценки по разным чек-листам. Облачные ASR/LLM настраиваются из административной панели.

**[УТВЕРЖДЕНО]** Два бизнес-статуса *результата оценки*: «Полная оценка» и «Требуется вмешательство человека». Они не заменяют технический статус конвейера обработки.

**[РЕКОМЕНДОВАНО]** Цель первой поставки — работоспособный фундамент: вход по логину/паролю, интерфейс, оргструктура, пользователи/сотрудники, роли/права, аудит. Далее независимо поставлять ручной импорт, карточку звонка, ИИ, конструкторы и аналитику. Все функции, объявленные будущими, допускаются в навигации только с явно недоступным состоянием; не делать фиктивные действия.

## 2. Стек и архитектурный подход

- Backend: актуальная совместимая стабильная версия PHP + Laravel с зафиксированными версиями в lock-файлах; JSON REST `/api/v1`; Laravel Form Requests, Policies/Gates, события, очереди, транзакции, сервисные классы.
- Frontend: Vue 3 + TypeScript, Vite, Pinia, Vue Router, единая дизайн-система; клиентский UI **не является** защитой доступа.
- MySQL 8.x/InnoDB/utf8mb4, миграции, индексы, FK, транзакции.
- Redis для очередей/кэша и Horizon для отслеживания фоновых задач, при совместимом окружении.
- FFmpeg/ffprobe для анализа и подготовки аудио; локальное защищённое хранилище в разработке, S3-совместимое в эксплуатации.
- Модульный монолит: доменные контексты `Identity`, `Organization`, `CallIntake`, `Audio`, `Transcription`, `Workflow`, `Evaluation`, `Review`, `Analytics`, `Integrations`, `Audit`, `AiProviders`.
- Переменные секретов — `.env`/secret manager; значения API-ключей в БД только в зашифрованном виде, если требуется управление ими из админки; никакого возврата полного секрета в UI или лог.
- OpenAPI, PHPUnit/Pest, Vitest, e2e-тесты критических сценариев; CI с lint/static analysis/tests/migrations.

**[РЕКОМЕНДОВАНО]** Не делать микросервисы в первой версии. Интерфейсы адаптеров сохраняют возможность вынесения тяжёлого аудиоконвейера в отдельные воркеры позже.

## 3. Организационная модель и идентичности

Структура: **группа компаний → компания → дилерский центр → отдел → сотрудник**. Пользовательская учётная запись `User` отделена от сотрудника `Employee`: у сотрудника может не быть учётной записи; одна учётная запись при необходимости связывается с сотрудником. Не путать `User`, `Employee` и `CallParticipant` (говорящий).

**[РЕКОМЕНДОВАНО]** У сотрудника допустимы несколько назначений в компаниях/отделах с датами начала/окончания. В карточке звонка сохранять исторический снимок организации и назначений, чтобы перемещение сотрудника не меняло старые отчёты.

### 3.1. Авторизация и права

**[УТВЕРЖДЕНО]** Вход по логину и паролю; пользователь — роль. **[РЕКОМЕНДОВАНО]** Использовать RBAC с возможностью нескольких ролей и областей действия; итоговые права = разрешённые действия × разрешённая область (группа/компания/центр/отдел/собственные записи). В интерфейсе показывать права пользователя, а доступ на сервере проверять на **каждом запросе и при выдаче файла**.

Начальные шаблоны ролей:

| Роль | Область | Основные права |
|---|---|---|
| Суперадминистратор | Вся группа | Пользователи, политики, интеграции, роли, конфигурация, аудит |
| Администратор компании | Назначенные компании | Оргструктура, назначения, сценарии, настройки в своей области |
| Директор / руководитель группы | Назначенные единицы | Аналитика, звонки, поручение проверок |
| РОП / руководитель отдела | Отделы | Звонки, аналитика, комментарии, инициирование апелляции |
| Контролёр качества | Назначенные подразделения | Слушать, исправлять транскрипт/оценки, решать проверки с аудитом |
| Сотрудник (опциональная учётная запись) | Собственные записи | Просмотр разрешённых оценок, обращение на пересмотр |

**[РЕКОМЕНДОВАНО]** Нет публичной регистрации. Суперадминистратор создаёт начальных администраторов; последующие пользователи заводятся назначенными администраторами в пределах их областей доступа. Пароли хешируются штатным безопасным алгоритмом; восстановление пароля по безопасной одноразовой ссылке; ограничение попыток, безопасные сессии, возможность завершить сессии; MFA для администраторов как обязательная опция до промышленного запуска.

Матрица granular permissions: `users.view/create/update/disable`, `roles.manage`, `organization.manage`, `calls.view/upload/delete/reprocess`, `audio.play/download`, `transcript.view/edit`, `evaluation.view/override/finalize`, `review.assign/resolve`, `appeal.create/resolve`, `workflow.design/publish`, `checklist.design/publish`, `integrations.manage`, `ai.manage`, `analytics.view/export`, `audit.view`. **Запрет по умолчанию**.

## 4. Модульная система источников звонков

### 4.1. Единый договор адаптера

Контракт сервиса `CallSourceDriverInterface` содержит: `getCapabilities()`, `validateConfiguration()`, `testConnection()`, `fetchBatch(cursor, window)`, `resolveRecording(externalCallId)`, `normalize(payload)`, `verifyWebhook(request)` (только для поддерживающих webhook источников). Система должна поддерживать как pull, так и push; методы, неподдерживаемые конкретным модулем, явно объявлены capabilities.

Каждый источник возвращает нормализованную сущность: `source`, `external_id`, направление, дата/время с timezone, номера (при наличии), длительность, идентификаторы участников/добавочных, компания/подразделение (если установлены), список записей, метаданные и сырой provider payload в защищённом виде.

**Обязательное:** `source + external_id` (с учётом области подключения) — идемпотентность; хранить внешние идентификаторы и события, время синхронизации, ошибки; повторные запросы не создают дубликатов. Для ручного источника ID генерирует портал. При объединении источников не склеивать разные звонки по одному номеру телефона без надёжной связи; предлагать ручное связывание при неопределённости.

### 4.2. Ручная загрузка — ядро [УТВЕРЖДЕНО]

Поддержать одиночную/пакетную загрузку (MP3, WAV, M4A после проверки содержимого, MIME и технической читаемости), выбор компании, центра, отдела, сотрудника, направления/сценария; возможность указать администратора/оператора и примечание; прогресс, список результатов и ошибок. Проверять права, размер, длительность, квоты; сохранять оригинал в приватном хранилище, вычислять хеш и сообщать о вероятных дублях (не удалять без подтверждения). Ограничения на длительность и размер — конфигурируемые и устанавливаются после пилота.

### 4.3. Отдельный модуль Calltouch [УТВЕРЖДЕНО]

Подключение и отключение без изменения ядра, собственные конфигурации и доступы, логи синхронизации. **[ТРЕБУЕТ ПРОВЕРКИ]** Возможности аккаунта, API, вебхуков, аудио и маркетинговой атрибуции подтверждаются по реальной документации/тарифу. Не писать выдуманный код интеграции до проверки API; разрешён контракт и mock-адаптер.

### 4.4. Отдельный модуль «Лягушка» [УТВЕРЖДЕНО]

Ровно тот же подход: отдельный адаптер, конфигурация, расписание/вебхуки, диагностирование. **[ТРЕБУЕТ ПРОВЕРКИ]** Уточнить официальное название телефонии, схему идентификаторов, авторизацию, получение аудио, правила лицензирования и доступность тестовой среды.

## 5. Конвейер звонка и жизненный цикл

1. Приём/регистрация звонка и источника.
2. Обогащение и маршрутизация в организационной структуре; при неопределённости — ручное сопоставление.
3. Валидация записи, доступности, дублирования и пригодности.
4. Сохранение оригинала и нормализация копии (FFmpeg).
5. Распознавание ASR с временными метками.
6. Диаризация и определение ролей; имя из речи — **гипотеза**, не верификация личности.
7. Классификация разговора, определение бизнес-процесса и набора чек-листов.
8. Оценка каждого чек-листа, проверка доказательств, формирование рекомендаций.
9. Автоматическая валидация структуры и результата; установка бизнес-статуса оценки.
10. Сохранение immutable analysis run, уведомление/задача ручной проверки при необходимости.
11. Обновление агрегатов и отчётов.

**Технический статус** `received`, `awaiting_audio`, `queued`, `preparing`, `transcribing`, `classifying`, `evaluating`, `completed`, `failed`, `excluded`. Перезапуск должен быть идемпотентным, с сохранением истории попыток, причин ошибок и времени каждого шага. Прогресс отражает реальные этапы, без фиктивных процентов.

**Бизнес-статус оценки** (только если получен результат анализа):
- `full_assessment` — «Полная оценка»: все обязательные применимые пункты имеют достаточные доказательства, структурные проверки пройдены, открытых обязательных ручных задач нет. **Не означает**, что человек подтвердил результат.
- `human_intervention_required` — «Требуется вмешательство человека»: неуверенность, невозможность установить говорящего/сотрудника при обязательности, противоречие, некорректные доказательства, обязательный `unknown`, критическая ситуация по правилам.

Дополнительно отдельно: `review_state` = `not_required`, `pending`, `in_progress`, `resolved`; и `approval_state` = `unreviewed`, `human_confirmed`, `human_overridden`. Не создавать итоговую оценку для звонков без аудио или с невосстановимой ошибкой.

## 6. Визуальный редактор бизнес-процессов [УТВЕРЖДЕНО]

**Принцип:** CRM-подобный визуальный граф узлов с направленными связями, условиями, ветвлениями и действиями. Реализация — редактор Vue на проверенной graph/node библиотеке (например, Vue Flow), **серверный** интерпретатор в Laravel. UI не исполняет сценарии; он формирует/проверяет описание графа.

### 6.1. Модель и узлы

`workflow_definitions` (name, scope, description, draft/published/archived), `workflow_versions` (JSON graph, schema_version, author, published_at, immutable), `workflow_triggers`, `workflow_runs`, `workflow_node_runs`, `workflow_execution_logs`.

**Узлы v1:** старт (поступил звонок / завершено распознавание / завершена оценка / ручное событие), проверка условия (`if/else`), выбор по нескольким значениям (`switch`), назначить сотрудника/отдел, выбрать основной чек-лист, добавить дополнительные чек-листы, запустить анализ, создать задачу человеку, изменить метку/приоритет, отправить уведомление (если включено), завершение. Условия только из **whitelist** доступных полей и типизированных операторов; никакого `eval`, произвольного PHP/JS/SQL из админки.

**Примеры условий:** направление звонка, источник, компания/центр/отдел, подтверждённый тип разговора, длительность, качество распознавания, полнота результата, наличие критических нарушений, статус оценки. Схемы переменных и допустимых значений документировать.

**Ветвления:** минимум `true/false`, несколько альтернатив, default ветка; узлы могут сойтись обратно. **[РЕКОМЕНДОВАНО]** В v1 граф ациклический (DAG), без произвольных циклов и параллельного исполнения одного и того же шага; отложенные действия/таймеры — отдельная следующая версия. При публикации сервер проверяет достижимость, отсутствие циклов, корректность связей, типы входов/выходов, допустимые действия и наличие завершающего пути.

### 6.2. Публикация и исполнение

Черновик → валидация → симуляция на тестовых данных → публикация версии. Запущенный экземпляр использует **фиксированную опубликованную версию**, даже если администратор редактирует новый черновик. Хранить входные данные, выбор веток, результаты шагов, время и причины ошибок; шаги выполнять идемпотентно. Ограничения на число узлов, глубину графа, ресурсы и повторы. Ручной запуск и повтор выполнения — только по правам, с аудитом.

**Важно:** бизнес-процесс задаёт *когда и как* обрабатывать звонок; чек-лист задаёт *как оценивать* разговор. Это два разных конструктора.

## 7. Конструктор чек-листов и правила оценки

**[УТВЕРЖДЕНО]** Чек-листы создаются и настраиваются администратором; один звонок имеет **ровно один основной** и **ноль или более дополнительных** чек-листов, выбранных опубликованным процессом. Результаты каждого чек-листа хранятся независимо.

Поля критерия: код, заголовок, описание, подсказки для ИИ, вес, обязательность, критический признак, тип (`binary` для v1), применимость, инструкция определения выполненности, допустимые доказательства и требования к ручной проверке. Версии чек-листов неизменяемы после публикации. Добавление/изменение создаёт новую версию; старые результаты не переписывать.

### 7.1. Рекомендуемая временная формула [РЕКОМЕНДОВАНО]

Для каждого применимого критерия `i` с весом `w_i > 0`: `pass` = `w_i`, `fail` = `0`; `not_applicable` исключается из знаменателя. Если любой **обязательный применимый** критерий = `insufficient_data`, ставить «Требуется вмешательство человека», **не публиковать итог как полную оценку**. Для необязательного `insufficient_data` также требуется ручная проверка соответствующего критерия; общий автоматический результат помечен требующим вмешательства до разрешения. Не подменять `unknown` значением `fail` или `N/A`.

`score = round(100 × Σ(w_i × pass_i) / Σ(w_i))`, где суммирование идёт по применимым критериям с разрешённым статусом `pass`/`fail`. Если знаменатель равен нулю, итог `null`, а не 0. При наличии неизвестных критериев можно вычислить технический предварительный интервал/частичный результат, но **не показывать единое окончательное число** в рейтингах до ручного разрешения. Округление и политика отображения должны иметь собственную версию правила.

**Критическая ошибка [РЕКОМЕНДОВАНО]:** фиксировать отдельным флагом; автоматически **не обнулять** оценку всего чек-листа. Допускается конфигурируемое правило «оценка обнуляется при критическом нарушении» на уровне *версии чек-листа*, выключенное по умолчанию, с обязательным пояснением и аудитом. Пока неизвестны реальные чек-листы, демонстрационные критерии помечать DEMO и не использовать для кадровых выводов.

**Главный и дополнительные результаты:** не смешивать в единую цифру по умолчанию. Главная оценка — из основного чек-листа. Дополнительные — отдельные 0–100 и отдельные критические признаки, с названием и версией; агрегированную комбинированную оценку вводить только после утверждения бизнес-формулы.

### 7.2. Доказательства

`evidence.type`: `quote` (проверенный сегмент текста), `time_range` (отрезок разговора/отсутствие действия), `source_metadata` (АТС/CRM), `manual_note`. Цитаты должны ссылаться на реальные сегменты транскрипта; говорящий/таймкоды валидируются сервером. Критерий «не предложил тест-драйв» нельзя доказывать выдуманной цитатой: использовать оценку полноты диапазона разговора и объяснение ограничения. При неясном аудио/неполном транскрипте — неизвестно и проверка.

### 7.3. Демо-процессы и чек-листы [РЕКОМЕНДОВАНО]

Создать редактируемые **демонстрационные** версии:

- «Входящий — продажа»: приветствие и представление, выяснение запроса, уточняющие вопросы, предложение следующего шага, подтверждение договорённостей, завершение.
- «Исходящий — контакт»: идентификация клиента, цель звонка, согласование дальнейшего действия, завершение.
- Дополнительный «Стандарт коммуникации»: корректность, вежливость, понятная речь, недопустимость некорректных формулировок.

Веса демо-критериев выбирать произвольно лишь как тестовые и явно маркировать. Предусмотреть в админке редактирование критериев и веса, применимости, публикации версий, тестирование на эталонном звонке и просмотр сравнения версий. **Не выдавать демо за корпоративный стандарт.**

## 8. Настройка облачных ИИ-провайдеров [УТВЕРЖДЕНО]

Раздельные адаптеры `SpeechToTextProviderInterface` и `EvaluationProviderInterface`; админка: список провайдеров, название конфигурации, ключ/API endpoint, модель, таймауты, лимиты запросов, выбор основной/резервной модели, тест подключения, история ошибок, оценка стоимости и статистика вызовов. Активные ключи не раскрывать в UI или логах; изменение секрета — отдельная операция.

Для каждого вызова хранить безопасные метаданные: имя провайдера/модели, параметры, версию prompt, hash входа, время, токены/минуты, стоимость (по конфигурируемому тарифу), код ошибки, retries. Не хранить необезличенные payload в обычном application log. Разграничить права на изменение провайдера и просмотр журналов.

**[ТРЕБУЕТ ПРОВЕРКИ]** Конкретные провайдеры, контракты, поддержка временных меток и диаризации, политика хранения провайдера, регионы обработки, стоимость, правовые основания передачи и договоры. Разрешение использовать внешние API означает архитектурный выбор, **не автоматическое подтверждение правомерности любой передачи данных**.

Ответ ИИ: строгая JSON-схема с `checklist_version_id`, `criterion_id`, `status`, `reason`, `evidence_refs`, `confidence` (внутренняя эвристика, не статистическая гарантия), `risks`, `recommendations`; сервер валидирует схему и ссылки. При нарушениях — контролируемая повторная попытка и/или ручная задача. Prompt/транскрипт трактуются как недоверенные данные; не выполнять инструкции из речи клиента.

## 9. Карточки, экраны и UX

**Первые экраны:** вход; мастер инициализации первого администратора (защищённый CLI или одноразовый setup); каркас портала с боковым меню/хедером; профиль/сессии; пользователи; роли/матрица прав; группы компаний, компании, центры, отделы, сотрудники; журнал аудита; экран недоступного модуля без ложных функций.

**Дальнейшие экраны:** ручная загрузка; история звонков с фильтрами и сохранёнными представлениями; карточка звонка (аудиоплеер, текст с таймкодами, говорящие, основной+дополнительные чек-листы, доказательства, рекомендации, история версий, кнопка отправки на проверку); очередь; ручная проверка и апелляции; визуальный конструктор процессов (canvas, palette, свойства узла, предпросмотр маршрута, симулятор, публикация); конструктор чек-листов; управление источниками и ИИ; дашборд и экспорт.

При проектировании UX использовать изображение на последней странице исходного ТЗ как *функциональный референс*, не копировать буквально размытые детали. Десктоп приоритетен; адаптивная версия обязательна хотя бы для просмотра и управления основными задачами.

## 10. Аналитика и конверсия

KPI: количество звонков, пригодные/исключённые, доля обработанных, основная средняя оценка по **финальным** результатам, доля критических нарушений, распределение по сценариям, очереди ручных проверок, длительность и стоимость анализа, динамика компаний/центров/сотрудников. Всегда показывать период, объём выборки, методику исключения, версию чек-листа и источник финальности. Дополнительные чек-листы не участвуют автоматически в главном среднем.

**[РЕКОМЕНДОВАНО]** Разделить: `conversation_agreement` — обещанное действие, извлечённое из разговора; `crm_confirmed_conversion` — подтверждённое внешней системой событие (пока CRM нет — поле «нет данных», не 0). Не объединять их в один KPI. Пропущенные звонки без аудио учитывать как количество, но не оценивать по разговору.

## 11. Ручная проверка, апелляции, правки

**[РЕКОМЕНДОВАНО]** Контролёр может исправить транскрипт или критерий с обязательной причиной; решение формирует новый снимок результата, не меняет первоначальный. Результат ИИ, проверенное человеком и итоговый результат — раздельные поля/версии. Сотрудники с доступом могут отправлять апелляцию, если соответствующий permission включён; РОП видит статус, но не утверждает собственную апелляцию без специального права. Апелляция назначается независимому контролёру или уполномоченному руководителю. Все действия — с автором, временем, причиной, старым и новым значениями.

## 12. Данные, безопасность, хранение

**[УТВЕРЖДЕНО]** Портал закрытый; политика обработки данных размещается на сайте; внешние ИИ-провайдеры допускаются.

**[РЕКОМЕНДОВАНО]** Отдельно от публикации политики установить юридические основания записи/обработки и передачи, назначить ответственное лицо, проверить применимое право и провайдеров перед реальными данными. Публикация текста на закрытом сайте **сама по себе не заменяет** обязательные процедуры. Это пункт юридической проверки, не утверждение о наличии нарушения.

Технически: HTTPS, защищённые cookies/session либо защищённая аутентификация для SPA, CSRF по используемой схеме, RBAC с областью, throttling, серверные проверки, антивирус/сканирование файлов при необходимости, ограничения загрузки, приватные ссылки с коротким TTL или streaming через авторизованный endpoint, audit read/download sensitive resources по настройке, маскирование телефонных номеров в UI по правам, секреты/ключи зашифрованы, бэкапы БД + аудио + конфигурации, регулярная проверка восстановления.

**[РЕКОМЕНДОВАНО]** Сроки хранения делать настраиваемыми по категориям (оригинал, транскрипт, результаты, аудит, бэкап), default **не задавать в днях до согласования**; поддержать удаление/анонимизацию по процедуре с документированными исключениями. Не отправлять реальные звонки в внешние API до включения обработки ответственным администратором и завершения юридической проверки.

## 15. Этапы реализации, которые давать ИИ-агенту по отдельности

### Этап A — FOUNDATION (первое задание агенту) [РЕКОМЕНДОВАНО]

1. Инициализировать совместимый Laravel + Vue 3 + TypeScript + MySQL проект; README, `.env.example`, миграции, линтеры, базовые тесты.
2. Спроектировать модель организации и различие `User/Employee`, роли и разрешения с областью; сидеры демоданных **без реальных персональных данных**.
3. Реализовать вход по логину/паролю, восстановление, сессии, запрет публичной регистрации, bootstrap admin через защищённую команду.
4. Реализовать layout, меню, breadcrumbs, таблицы/формы управления компаниями, центрами, отделами, сотрудниками, пользователями, ролями.
5. Серверные policies, scoped queries, аудит изменений; позитивные и негативные тесты доступа между компаниями.
6. Создать страницы-заглушки остальных разделов с понятной пометкой «В разработке» — никаких фальшивых метрик/записей в рабочем интерфейсе.

**Приёмка A:** админ управляет справочниками и ролями; директор компании A не получает записи/пользователей компании B через API/экспорт; вход, logout, сброс и ограничения сессий проходят тесты; нет hardcoded permissions в Vue как единственного барьера; migrations up/down проверены.

### Этап B — MANUAL INTAKE

Загрузка файлов, метаданные, приватное хранилище, дедупликация, история, карточка звонка, аудиоплеер, очередь задач и технические статусы. **Приёмка B:** корректный аудиофайл импортируется один раз; повреждённый отклоняется с диагностикой; доступ к чужому файлу закрыт; повтор выполнения не дублирует сущности.

### Этап C — AI PIPELINE

Облачный ASR/LLM через сменяемые интерфейсы, конфигурация ключей в админке, транскрипт, evidence validation, стоимость, тесты на mock-провайдере. **Приёмка C:** таймкоды проверяемы, ошибки API не теряют звонок, ответы с придуманными доказательствами отправляются на проверку.

### Этап D — CHECKLISTS + WORKFLOW DESIGNER

Конструктор версионируемых чек-листов, основной и дополнительные результаты; визуальный граф, условия, ветвления, симуляция/валидация/публикация, серверный исполнитель. **Приёмка D:** администратор без изменений кода настраивает «если входящий и отдел продаж → основной Продажи + дополнительный Стандарты → оценить; если недостаточно данных → проверка»; после публикации новая версия не меняет уже запущенные экземпляры.

### Этап E — HUMAN REVIEW + ANALYTICS

Проверка, ручные правки и апелляции, история оценок, аналитика с честными знаменателями, отчёты и экспорт. **Приёмка E:** автоматический и исправленный результаты различимы; неизвестные оценки не искажают среднее; журнал изменений полон.

### Этап F — EXTERNAL CONNECTORS + PILOT

Calltouch и «Лягушка» отдельными адаптерами после получения документации и доступов, выборка эталонных звонков, настройка точности/стоимости/производительности, нагрузочные и восстановительные тесты. Не считать этап завершённым на одних моках API.

## 16. Минимальный набор обязательных тестов

- Пользователь компании A не может увидеть/изменить данные B, включая бинарные аудиофайлы и выгрузки.
- Дублированный импорт и повторение фоновой задачи не создают двойную оценку/файл.
- Потеря подключения к модели, timeout, 429, 500, плохой JSON: безопасная повторная попытка/эскалация с сохранением аудио.
- Отредактированный опубликованный чек-лист не меняет старых оценок; публикация создаёт новую версию.
- workflow без завершения, с недостижимыми узлами, циклами или запрещёнными действиями не публикуется.
- Для одного звонка сохраняются отдельные результаты основного и дополнительных чек-листов; в основной KPI не попадают дополнительные оценки.
- `insufficient_data` не превращается в `fail` и не маскируется как окончательная оценка.
- Цитаты несуществующих сегментов, невозможные таймкоды, рассогласование говорящего — отклоняются валидатором.
- Проверка человеком не затирает оригинал; аудит содержит автора, дату, основание и diff.
- API-ключи недоступны в response/log, обычному администратору без permission нельзя менять ИИ-провайдера.

## 17. Риски и пункты, не закрытые ответами

**До промышленной обработки реальных звонков необходимо установить:** юридические основания записи, допустимость внешних провайдеров и условия договоров; сроки хранения; реальную нагрузку и бюджет; API Calltouch и «Лягушки»; эталонные критерии точности; согласованный SLA. Это не блокирует этап A на синтетических данных.

**Решения по умолчанию, принятые для развития без дополнительных вопросов:**

1. **Переводы звонков:** данные об участниках и частях разговора хранить сразу; оценку каждого участника в MVP запускать только по явно выделенному сегменту либо направлять на проверку, если сегментация ненадёжна.
2. **Личный кабинет сотрудника/апелляции:** архитектурно предусмотреть, UI и workflow апелляции включать на этапе E; по умолчанию сотрудник не видит чужие разговоры.
3. **Переоценка после изменения чек-листа:** только явным действием уполномоченного пользователя, с новым analysis run; никакого фонового массового пересчёта.
4. **Ручная идентификация:** назначение компании и сотрудника при загрузке обязательно лишь если доступно; можно выбрать «Не установлен» с задачей разрешения, не подставлять случайного сотрудника.
5. **Управление ролями на уровне компаний:** админ компании назначает разрешённые роли только в своей области; создание/редактирование глобальных прав — привилегия супер-администратора.
6. **Сроки хранения:** configurable policy по категориям, без выдуманного числового срока; окончательное значение согласовать юридически и операционно.
7. **Размер файлов:** конфигурируемые лимиты, chunked/resumable upload для больших записей как развитие; ограничения выбирать после пилота на образцах реальных файлов.
8. **Точность и SLA:** методика обязательна до пилота; численные пороги утверждаются после анализа эталонной выборки.
9. **Конверсия:** отличать договорённость из транскрипта от подтверждения факта в CRM; без CRM второй показатель отсутствует.
10. **Демо:** исключительно фиктивные или разрешённые тестовые записи и явно маркированные DEMO-чек-листы; запрещено выдавать их оценки за производственные.
